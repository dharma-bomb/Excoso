# Deploying this repo

This is your full Laravel application source, ready to `git init` and push
to GitHub. A few things are deliberately **not** in here, and one thing
about the folder layout is worth understanding before you deploy.

## Your site uses a "flattened" cPanel layout — this repo matches that

Normally in Laravel, `index.php`, `.htaccess`, `favicon.ico`, and
`robots.txt` live inside a `public/` folder, and `public/` is the only
folder the web server points at directly.

Your live site isn't set up that way. Looking at what you sent me:

- `index.php` requires `__DIR__.'/vendor/autoload.php'` and
  `__DIR__.'/bootstrap/app.php'` directly (a normal Laravel `public/index.php`
  says `__DIR__.'/../vendor/autoload.php'` — one level up).
- `.htaccess` has a cPanel-generated PHP-version block in it.
- There was no `public/` folder at all in what you sent — `index.php`,
  `.htaccess`, `favicon.ico`, and `robots.txt` sit at the project root.

That's the classic cPanel setup for Laravel: the domain's document root
*is* the project root, and the contents of `public/` were copied up to
the top level (with `index.php`'s paths adjusted) because shared cPanel
hosting usually can't point a domain at a subfolder or use symlinks. This
repo is packaged to match that — don't move `index.php`/`.htaccess` into
a `public/` folder unless you're also changing how the domain is served.

If you ever move to hosting where you *can* point the domain straight at
a `public/` folder (many non-cPanel hosts, or a VPS), you'd restore the
standard layout instead: put `index.php`, `.htaccess`, `favicon.ico`, and
`robots.txt` in a `public/` folder, change `index.php`'s two `__DIR__.'/...'`
paths back to `__DIR__.'/../...'`, and point the web server at `public/`.
Only do this if you're intentionally changing hosting — not needed to keep
running on cPanel as-is.

## What's NOT in this zip, and why

- **`vendor/`** — Composer dependencies. Never belongs in git. Restore with:
  ```
  composer install --no-dev --optimize-autoloader
  ```
- **`node_modules/`** — npm dependencies, same reasoning. Restore with `npm install` (only needed if you rebuild front-end assets with Vite; the live site's actual product/marketing pages are plain Blade + CSS, not a Vite build).
- **`.env`** — contains your real database password, mail credentials, and app key. Never belongs in git. Only `.env.example` (the blank template) is included. On the server, copy it to `.env`, fill in your real values, then run `php artisan key:generate` if `APP_KEY` is empty.
- **`database/database.sqlite`** — your real product/category/admin data. Your own `database/.gitignore` already excludes `*.sqlite*`, so this repo follows that same rule. Your live server already has this file in place; don't overwrite it with an empty one. (If you ever need a fresh copy: `touch database/database.sqlite && php artisan migrate`.)
- **`bootstrap/cache/services.php` and `bootstrap/cache/packages.php`** — these are compiled caches Laravel regenerates automatically (`php artisan config:cache` / `composer install` rebuild them). They should never be committed — a stale one from a different PHP/Composer setup is a common cause of fatal errors like "Class Illuminate\Foundation\Application not found" or "Call to undefined function env()", both of which show up in the old error logs from your live server. If you hit either error again after deploying, delete everything in `bootstrap/cache/` except its `.gitignore` and reload.
- **cPanel housekeeping files** (`.htaccess.lock-*`, `.htaccess.phpupgrader.*`) and stray `error_log` files — these were auto-generated by your hosting control panel / PHP itself, not part of the application. Left out of a clean repo on purpose.

## First deploy from this repo, step by step

1. `git init`, commit everything in this zip, push to GitHub.
2. On the server (or via cPanel's Git/Composer tools): `composer install --no-dev --optimize-autoloader`.
3. Copy `.env.example` to `.env`, fill in real DB + mail values matching your cPanel MySQL/SQLite setup, then `php artisan key:generate` if needed.
4. Make sure `database/database.sqlite` exists (your real one, or a fresh migrated one — see above) and is writable by PHP.
5. Make sure `storage/` and `bootstrap/cache/` are writable by PHP (standard Laravel permissions requirement).
6. Re-upload your real product photos. Worth double-checking exactly where: the code uploads/reads them via `public_path('images/addproduct/...')`, which normally means `<project root>/public/images/addproduct/`. But since your `index.php` is flattened to the project root instead of living inside `public/`, the site's image URLs (`/images/addproduct/...`) point at `<project root>/images/addproduct/`, not `<project root>/public/images/addproduct/`. If product images were already displaying correctly on your live site before this update, whatever folder they're currently in is the right one — just put them back in that same spot. If you're setting this up fresh, put them in both `public/images/addproduct/` and `images/addproduct/` and see which one the live site actually serves, then keep only that one. Your `public/` folder itself (build assets, storage symlink, etc.) was never part of what you sent me either, so it isn't in this zip.
7. Run `php artisan migrate` to create the new `quote_requests` table (needed for the redesigned homepage's "Get a Quote" form — see `CHANGES.md`).
8. Put the new `public/css/theme.css` file (already in this zip at that path) in the **same folder on your server where your existing `css/navbar.css`, `css/style.css`, etc. currently live** — by the same flattened-layout logic as step 6, that's most likely `<project root>/css/theme.css` rather than `<project root>/public/css/theme.css`, but whichever folder your existing CSS files are actually being served from is the right one.
9. If you want the "Get a Quote" form to actually deliver email to `sales@expertcorporatesolutions.com` (rather than just saving to the database and to `/admin/quotes`), set real `MAIL_MAILER`/`MAIL_HOST`/`MAIL_USERNAME`/`MAIL_PASSWORD` values in `.env` — they're still Laravel's placeholder defaults in both the `.env` you sent me and `.env.example`. Until then, submissions still save correctly; they just won't leave the server as an email.

See `CHANGES.md` for what changed in this pass — product Edit/Delete, a login security fix, and (new) the homepage redesign merged into your live templates with a real "Get a Quote" backend.
